# Development environment

BannerMania gets a reproducible, declarative development environment. Two
contributors on different machines, and CI on a clean runner, must resolve the
same toolchain from files committed to the repository — never from whatever
happens to be installed on the host.

This project is a single Python 3.14 web application (Flask + Pillow) that
renders banner PNGs and animated GIFs. It has no AWS infrastructure, no
container image, and no networked runtime dependencies, so the toolchain below
is scoped to what this app actually needs. If a later spec adds infrastructure
or a runtime service, extend this document deliberately at that point rather
than pinning tools the code does not use yet.

## Toolchain

| Tool | Owns | Where it is declared |
|------|------|----------------------|
| **devbox** | The whole non-Python toolchain, pinned per project | host prerequisite; manages `devbox.json` |
| **direnv** | Activating that toolchain on `cd`, deactivating on exit | host prerequisite; reads `.envrc` |
| **python** | The interpreter version (3.14, matching `requires-python`) | `devbox.json` package |
| **uv** | Python dependency resolution, locking, and the project virtual environment | `devbox.json` package; owns `pyproject.toml` + `uv.lock` |
| **just** | The documented command surface — test, lint, run, package | `devbox.json` package; recipes in `Justfile` |
| **jq** | JSON inspection in recipes and scripts | `devbox.json` package |
| **yq-go** | YAML inspection in recipes and scripts | `devbox.json` package |
| **git** | Version control, and the hook behavior CI depends on | `devbox.json` package |
| **gh** | Pull requests, releases, CI runs from the terminal | `devbox.json` package |

### Host prerequisites versus project packages

**devbox and direnv are host prerequisites, not project packages.** Devbox
cannot install itself, and direnv has to be on the shell *before* you enter the
directory or there is nothing to trigger activation. Install direnv once with
`devbox global add direnv` so it is available across every project, and hook it
into your shell. Everything else in the table above belongs in this project's
own `devbox.json` so it is versioned with the code that needs it.

**git is a project package even though the host already has one.** You need some
git to clone the repository, but only the pinned one is on the PATH inside the
environment, so hooks (this project ships `.githooks/pre-push` and
`scripts/install-git-hooks.sh`), config resolution, and subcommand availability
behave the same for every contributor and on a clean CI runner. That is a
different case from devbox and direnv, neither of which can be supplied by the
environment they are responsible for creating.

## Required files at the repository root

- **`devbox.json`** — the package list. Created with `devbox init`, populated
  with `devbox add <pkg>@<version>`.
- **`devbox.lock`** — committed. This is what makes the environment
  reproducible; without it the resolved versions can drift.
- **`.envrc`** — generated by `devbox generate direnv`, containing
  `eval "$(devbox generate direnv --print-envrc)"`. Committed, then trusted
  locally with `direnv allow`.
- **`Justfile`** — every command a contributor or CI stage needs to run.
- **`.gitignore`** — must exclude `.devbox/` and `.venv/`, plus this project's
  generated banner artifacts (`*.png` / `*.gif`, keeping the committed `docs/`
  assets).

## Pinning

**Pin every devbox package to an exact version.** Devbox defaults an omitted
version to `@latest`, which pins nothing and lets the toolchain drift between
machines and between commits. This is the same rule the engineering practices
apply to application dependencies, extended to the tools that build them. The
versions below are the ones resolvable for this project; upgrade them
deliberately, as their own reviewable commit, never as a side effect of
someone else's checkout.

```json
{
  "packages": [
    "python@3.14.4",
    "uv@0.12.5",
    "just@1.58.0",
    "jq@1.8.2",
    "yq-go@4.53.3",
    "git@2.55.0",
    "gh@2.98.0"
  ]
}
```

Resolve each version with `devbox search <pkg>` and commit `devbox.lock`
alongside.

One package name needs naming deliberately rather than by guess, because the
obvious spelling resolves to the wrong thing:

- `yq` is the Python wrapper around jq; **`yq-go`** is the Go implementation most
  recipes assume. Pin `yq-go`.

(The generic workspace template also names `docker-client`, `docker-compose`,
`aws-cdk-cli`, and `awscli2`. None apply to this project and none should be in
`devbox.json` here — pin them only if a future spec introduces containers or
AWS infrastructure.)

## Python: devbox provides the interpreter, uv owns the dependencies

Do not install Python packages with the interpreter devbox provides. A
Nix-installed interpreter cannot write to its own store path, and installing
globally would defeat the per-project isolation devbox exists to give.

- `devbox.json` pins the **interpreter version** (3.14, matching
  `requires-python = ">=3.14"` in `pyproject.toml`).
- `uv` creates and manages the project virtual environment, resolves
  dependencies, and writes `uv.lock`.
- `pyproject.toml` is the single manifest for this app.
- `uv.lock` is committed. It is what satisfies the exact-version requirement the
  specs place on direct dependencies.

**The dividing line is import versus invoke.** Anything application or test code
`import`s is a uv dependency. Anything a recipe or a shell invokes is a devbox
package. For this project that means:

- **uv dependencies** (`pyproject.toml`): `flask` and `pillow` at runtime;
  `pytest`, `ruff`, and `detect-secrets` in the `dev` group. The `desktop-app`
  spec additionally adds `pyside6`, `hypothesis`, and `pyinstaller` — all
  imported or driven from Python — to `pyproject.toml`, not to `devbox.json`.
- **devbox packages** (`devbox.json`): `python`, `uv`, `just`, `jq`, `yq-go`,
  `git`, `gh` — each invoked from a shell or a recipe.

Note that `ruff` and `pytest` are invoked from recipes but are still uv
dependencies, because they are installed into the project virtual environment
uv manages rather than pinned as standalone Nix binaries. The import-versus-
invoke line is about *where a tool is installed from*, and these come from the
Python environment.

## just is the command surface

Every command named in a spec or a README is a `just` recipe, so there is one
documented way to run each thing and CI and a contributor invoke the same code
path. For this project, at minimum: `just test`, `just lint`, `just typecheck`
(once type checking is adopted), `just run` for the Flask app, and — for the
`desktop-app` spec — `just desktop` to launch the native app and `just package`
to build it with PyInstaller.

A spec that requires "the single documented test command" is satisfied by a
recipe, not by a shell snippet pasted into a README.

## Secret scanning

This project already defines its own credential scan rather than relying on a
generic entropy-based scanner: `detect-secrets` with a committed
`.secrets.baseline`, plus `scripts/check_pii.py` for the project's explicit PII
allowlist convention (see the `# allowlist pii:` marker in `pyproject.toml`).

A generic entropy-based secret scanner is a poor fit here and must not replace
that scan: the render code is full of RGB color tuples and hex color strings
that a character-class or length heuristic would flag as false positives. A
generic scanner may sit alongside as defense in depth; it must not be mistaken
for the required scan.

`pre-commit` is complementary to a pipeline check, never a substitute for one —
a hook that can be skipped locally is not an enforcement boundary. This project
installs its hooks via `scripts/install-git-hooks.sh` into `.githooks/`.

## Constraints this must not break

- **Offline test guarantee.** Having `gh` on the PATH must not make any test
  depend on network access. The `pytest` suite must pass with no network beyond
  localhost. The rendering engine and the desktop app run entirely in-process
  (see the `desktop-app` design), so nothing in the test path should reach out
  to a network.
- **No secrets in committed files.** Environment variables that carry secrets
  are supplied at runtime. `.envrc` may export non-sensitive configuration and
  must never contain a key, token, or credential path holding real material.
  Use a git-ignored `.env.local` or the platform secret store instead.

## Bootstrapping / reconciling this project

1. `devbox init` (already done), then `devbox add` each tool at an exact version
   from the pinning list above. Replace the current `@latest` entries and the
   `yq` wrapper with `yq-go`; add `git` and `gh`.
2. `devbox generate direnv` and `direnv allow` (`.envrc` is already present).
3. `uv` manages the environment; `uv add` new dependencies and commit `uv.lock`.
4. Write the `Justfile` recipes the specs and README refer to.
5. Keep `.devbox/` and `.venv/` in `.gitignore`.
6. Commit `devbox.json`, `devbox.lock`, `.envrc`, `Justfile`, and `uv.lock`
   together, so the environment is reproducible from that commit on.
